# StockWeave Decision Log

## Stage 10 — on-chain redeem / sell path (2026-09-23)

- D-705: **`redeem` is now a real on-chain instruction — the mirror image of `subscribe`**, closing the gap that a follower could buy the mirror basket but had no on-chain way back to cash ("what use is it if I can't sell the tokens I bought?"). `redeem(asset_qty)` **burns** `asset_qty` of a mirror asset from the holder (the holder signs the burn on their own ATA) and **transfers USDC back** from the strategy treasury to the holder (the `[b"vault"]` PDA signs the CPI — **no server key** on the exit path, exactly like buy/faucet). Atomic: shares out, cash in. The key soundness property: **`usdc_out` is computed on-chain from the published price, never supplied by the caller** — `usdc_out = asset_qty · price_u / 10^decimals` in u128 (`checked_mul` → `ExcessiveNotional` on overflow, `require!(usdc_out > 0)` → `PriceOutOfBounds`) — so unlike `subscribe`'s ±tolerance check there is **nothing to game**: a caller cannot ask to be paid more than the burn is worth at the on-chain mark. Reuses the **D-703 `AssetPrice` PDA** (`[b"price", strategy, mint]`) for the price and its `ASSET_PRICE_MAX_AGE_SECONDS = 86_400` freshness; guards: `asset_qty > 0` (`BadRedemption` 6025), strategy not paused (`StrategyPaused`), `asset.enabled` (`AssetDisabled`), price fresh & positive. **A treasury-solvency check — `require!(treasury.amount >= usdc_out, InsufficientTreasury)` (6026) — runs BEFORE the burn**, so an over-redeem the treasury can't cover reverts cleanly with **zero balance movement** (a redeem can never half-drain a treasury: no burn happens if the payout can't be made). New `Redeem` accounts struct (13 accounts, every `Account` field `Box`ed to keep `try_accounts` under the 4 KB SBF stack) + `Redeemed { strategy, seller, asset_mint, asset_qty, usdc_out }` event + errors `BadRedemption`/`InsufficientTreasury` (6025/6026). **Migration-free by design:** `redeem` only reads existing PDAs (strategy/asset/price) and touches token accounts — no field was added to any deployed struct, so every existing PDA still deserializes (same discipline as D-703/D-704). Consistent with the established precedent, `redeem` is **not added to the hand-built IDL** (neither are `subscribe`/`faucet_usdc` — the browser client and Node verifiers hand-encode; nothing consumes redeem via the Anchor TS client). Client: `redeemFromBasketOnchain` + `IX.redeem` in `web/lib/onchain.ts` build one `redeem` ix per held leg (account order matching the `Redeem` struct exactly, 5 legs/tx). UI: a **"Sell this mix"** action in the dashboard Quick-actions rail (`web/app/dashboard/page.tsx`), gated on `devnetSeeded()` + `hasAssetHoldings`; `sellBasket` in `web/components/dashboard/context.tsx` sizes each leg from the wallet's **real on-chain balance** (`uiAmount × 10^decimals`, a full exit) and redeems against the same official strategy the tokens were minted by, so the treasury that pays out is the one `subscribe` funded. Proven on Devnet 2026-09-23: upgrade tx `5TRhPZidXGt42qj6seNoC6Pco7MmxBYBLhHPdLNm8f2novCY5tmQju6B8tJWZmjP4BwN2WoByEXDdQTXmcF2st7R` (`stockweave.so` 538832 bytes, up from 510544); verifier `tests/run-redeem-direct.js` → `tests/stage10-redeem-evidence.json` (**pass**): faucet → `set_asset_price` ($100/OPENAI) → `subscribe` (1.0 OPENAI for $100) → **`redeem` 0.5 OPENAI → +$50** (redeem tx `31vZ7Eq7g6CxnyvB1EWUxyuYgD7mgrgJu1JsZzDpGYrEyxDqBeobcgtKgXFjETmf4uKsq1nYxd9w8CY1MSXgQR3k`; asset 6.05→5.55, seller USDC 4960→5010, treasury 640→590 — before+delta isolated to the redeem so re-runs still pass), then a **NEGATIVE** case redeeming (treasury + $1,000) worth of asset is **rejected on-chain with `InsufficientTreasury` (err 6026), balances unchanged**. Rejected: making `usdc_out` a caller arg (that is the exact hole this closes); burning before the solvency check (would let a redeem burn shares without a full payout / partially drain an under-funded treasury — the `require!` precedes `token::burn`); growing existing account structs (bricks deployed PDAs — D-703/D-704); leaving redeem as a no-op or off-chain "sell" (contradicts the everything-on-chain-even-on-Devnet directive and the whole point of holding real mirror tokens).

## Stage 9 — on-chain live-NAV proof-of-return (2026-09-23)

- D-704: **Proof-of-return is now tracked on-chain, forward from launch.** The gap it closes: a follower's honest "will this make me money?" had no track-record answer. A backtest was considered and **rejected as infeasible/dishonest** — the live price source (`lib/live-prices.js` → Jupiter `lite-api.jup.ag/price/v3`) is **spot-only** (no time series, only a 24 h change field), and the pre-IPO mirror assets have **no honest price history to back-fill** (see D-203). So the honest artifact is a NAV that starts empty at launch and **accumulates real on-chain snapshots going forward** — never back-filled. New `record_nav(nav_u)` appends one point to a **`NavHistory` ring-buffer PDA** (seeds `[b"nav", strategy]`, fixed `[NavPoint; 128]` where `NavPoint { ts: i64, nav_u: u64 }`, account space 2144). `nav_u` is the basket's **weight-faithful index rebased to $1.000000 at inception** in USDC micro-units (6 dp): `I_t = Σ w_i·(P_i,t / P_i,0) + w_cash`, `nav_u = round(I_t·1e6)` — the ratio form is weight-faithful (a raw `Σ w_i·P_i` would let high-priced names dominate). Inception prices `P_i,0` are captured **once** from the same real live Jupiter quotes into `tests/nav-basis.json` (a since-inception cost basis, written once, never hand-edited); the **on-chain ring is the verifiable artifact**, the basis is only the reference. `record_nav` is **creator/keeper-signed** (`has_one = creator`) — the READ+PROPOSE agent is never a signer, preserving the never-EXECUTE constraint (recording NAV is a keeper/oracle action, not an agent trade). **Zero-copy was required:** the 2 KB inline `[NavPoint; 128]` overflows the 4 KB SBF stack on `try_deserialize`/`try_accounts` (boxing was insufficient), so `NavHistory` is `#[account(zero_copy)]` behind an `AccountLoader` and worked in place via `load_init()`/`load_mut()` (init-if-needed: `load_init()` succeeds only while the disc is still zero, else fall back to `load_mut()`); this needs `bytemuck` (`derive` + `min_const_generics`) and explicit `_pad0`/`_pad1` so the `#[repr(C)]` struct is Pod with no implicit padding. The UI reads the whole track record in **one `getAccountInfo`** (`readNavHistory` in `web/lib/onchain.ts`, unwrapping the ring oldest→newest) and renders a blueprint `PerformancePanel` (`web/components/dashboard/ui.tsx`) with **honest empty / single-point states** — it never draws a curve from < 2 points and labels itself "On-chain · live-recorded," not a backtest. Proven on Devnet 2026-09-23: upgrade tx `3DseJMSZsp3GLxzQvFJSPJGUyNL4BnpiAGFNQeVc6xhvTjWJKRPn4oeJnAA99nuHAL7KS6wevQFajrr1cVT87AWK` (`stockweave.so` 510544 bytes); keeper `tests/record-nav.js` recorded real live-priced snapshots into both official rings (`ai-infrastructure` nav `2coBKvUW…` count 5, `-1.08%`; `space-deep-tech` nav `99LYs9Lo…` count 7, `+0.00%`); read-only verifier `tests/verify-nav.js` re-reads both rings from chain, checks disc/strategy/authority/monotonic-timestamps/inception-rebase, and writes `tests/stage09-evidence.json` (**all checks pass**). Rejected: back-testing on fabricated or borrowed price history (dishonest; violates D-203/no-fabrication); a naive level-weighted `Σ w_i·P_i` (not weight-faithful); appending the ring to an existing struct (would brick deployed PDAs — same reasoning as D-703); an inline (non-zero-copy) array (SBF stack overflow); recording NAV from the agent (would make it a signer on state it must not touch).

## Stage 8 — on-chain price-binding guard (2026-09-23)

- D-703: **`subscribe` and `execute_rebalance` are now price-bound on-chain**, closing the soundness gap where both accepted a client-supplied token quantity with no price check. Before: `subscribe(usdc_in, asset_qty)` let a buyer pay negligible USDC and mint unlimited mirror shares; `execute_rebalance(asset_qty)` could pay out the full guarded `notional` while burning ~0 asset (drained treasury). Fix: a new **separate `AssetPrice` PDA** (seeds `[b"price", strategy, mint]`, fields `strategy/mint/price_u/updated_at/bump`, space 89) holds a published price; `price_u` = USDC base units (6 dp) per whole 9 dp token = USD×1e6. `set_asset_price(price_u)` is **creator-signed** (`has_one = creator`) — the READ+PROPOSE agent never signs it, preserving the constraint. `subscribe` requires `usdc_in ≈ asset_qty·price_u / 10^dec` and `execute` requires `asset_qty ≈ (notional·1e6)·10^dec / price_u`, both within `PRICE_TOLERANCE_BPS = 100` (1%), with `ASSET_PRICE_MAX_AGE_SECONDS = 86_400` (24 h) freshness. New errors `BadPrice/PriceUnavailable/StalePrice/PriceOutOfBounds` (6020–6023) + `AssetPriceSet` event. **Migration-free by design:** the price lives in its own PDA, so `StrategyAsset`/`RebalanceProposal`/`ProposeArgs`/the propose route are untouched and every existing PDA still deserializes (appending fields to `StrategyAsset` would have bricked existing asset PDAs — rejected). Official baskets are priced by `tests/seed-onchain-strategy.js`, which now fetches **real live Jupiter quotes** (via the mainnet mints) and publishes one `set_asset_price` per non-cash mirror mint (unpriced assets revert `PriceUnavailable` rather than fabricating a number). Proven on Devnet 2026-09-23: upgrade tx `3mSTDS4rgDYZMmpbb3WLvDn7qY35d92GiGHmBhDf1FrARzFFiHmrU6ehjctVCmk1SBoizovAiNnuBriMyXNt2xKz`; Stage 6 (`tests/run-stage6-buy-direct.js` → `stage06-buy-evidence.json`) publishes $100/OPENAI, buys 1.0 for 100 USDC, and a $1-for-1.0 gamed buy is **rejected** with balances unchanged; Stage 7 (`tests/run-stage7-execute-direct.js` → `stage07-evidence.json`) sizes the trim from the price (0.05 OPENAI for $5) and a burn-dust-for-full-payout execute is **rejected** with the proposal left Approved. Rejected: enforcing via Pyth for pre-IPO assets that have no feed (see D-203); growing existing account structs (breaks deserialization); making the price a caller arg on subscribe/execute (that is the exact hole being closed).

## Stage 7 — real execute on Devnet (2026-09-23)

- D-702: `execute_rebalance` now performs a **REAL Devnet-mirror trim** — it no longer only records `Executed` (this reopens D-503 for the Devnet mirror world, exactly as Stage 6 did for the buy path). An approved trim proposal BURNS `asset_qty` of the asset's mirror token from the creator (creator authority signs the burn) and TRANSFERS the proposal's `notional` (whole USDC → 6 dp) from the strategy treasury back to the creator (the `[b"vault"]` PDA signs the transfer via CPI). Atomic: shares out, cash in. `asset_qty` is a new instruction arg sized off-chain from the live price (shares to trim); the USDC leg is fixed on-chain by the guarded `proposal.notional`, so the treasury can only ever pay out the amount the proposal was risk-checked against. Guards unchanged + one added: proposal must be Approved, unexpired, `proposal.mint == asset_mint`, strategy not paused, `asset_qty > 0` (`BadExecuteAmount`). **Creator-only** (`has_one = creator`) — the agent is never a signer on execute, preserving READ+PROPOSE-not-EXECUTE. All `ExecuteRebalance` accounts are `Box`ed to keep `try_accounts`' SBF stack frame < 4KB. Proven on Devnet 2026-09-23: upgrade tx `2cXDb5iyZWjVdLuFFLoZ59Tswy3833d5UbLWGMGuLD9r6zzPg2UXFeUzzNpRgeyVwbCsmnmn94g6wbaYUetMrqpX`; propose→approve→execute round-trip burned 0.4 OPENAI and returned $5 from treasury (execute tx `3uF8sGMJBp3qxWwfFzoyTjE7qBavGhRCPpAdixN6YrmBWWY1NjRBmgoZtZxvq7MRonrAhqNF5a63DGtP3VW8nCuT`), evidence `tests/stage07-evidence.json` via `tests/run-stage7-execute-direct.js`. Supersedes D-503 for Devnet. Rejected: leaving execute as a no-op record (contradicts the "everything on-chain even on Devnet" directive); making the USDC payout a caller arg (would let execute pay out more than the guarded notional).

## Phase 7 (2026-09-19)

- D-701: `fork_strategy(new_strategy_id)` creates INDEPENDENT on-chain state in one instruction: a new Strategy PDA (caller = sole creator, `parent_strategy` = source) + a new Rules PDA that COPIES the parent's rule template (version reset to 1). Authority isolation is automatic — every guard checks the fork's own `creator` (`has_one`), so the parent's owner has zero control over the fork. Scope decision: assets/agent-permissions are re-registered on the fork by the new owner (who has authority) rather than bulk-copied in `fork_strategy`, to keep the instruction bounded (no variable-length remaining_accounts). This still satisfies the Phase 7 gate (independent state + authority; fork owner changes a rule; parent cannot). Rejected: copying N asset PDAs in one instruction (unbounded) and copying the agent authority (would violate fork independence).
